# 中国观鸟记录中心（birdreport.cn）数据体量与后端架构分析

> 目的：为与「中国观鸟记录中心」的后续合作做背景准备。
> 最后更新：2026-07-02
>
> **可信度分级**（全文用这套标签）：
> - 🟢 **实测**：本仓库脚本跑通过、或官方年报/首页明确给出的数字。
> - 🟡 **可观测**：从对外 API 表面能直接看到的结构（客户端能拿到的东西）。

## 0. 一句话结论

birdreport.cn 是国内**最完整的民间鸟类公民科学数据库**，由**昆明朱雀会**运营，覆盖全国 ~94% 的鸟种、千万级观测记录。它的**内部数据库 schema 从未公开**（⚪），但从对外 API 能反推出一套**清晰的关系型数据模型**（🟡）：`用户 → 报告(清单) → 观测记录 → 物种`，外加地点/热点与审核（疑问/无疑问）两条支线。对外接口做了**重度反爬**（RSA 加密请求 + AES 加密响应 + 签名 + captcha 限流），这本身就说明：**认真的合作必须走官方数据共享通道，而不是爬虫**。

## 1. 数据体量

| 维度 | 数值 | 来源/可信度 |
|---|---|---|
| 数据起点 | 平台 2014-05 上线；派生数据集回填到 1980/1997 | 🟢 官方首页 / 第三方数据集 |
| 运营方 | 昆明朱雀会 | 🟢 |
| 鸟种覆盖 | 覆盖全国约 **94%** 的鸟种 | 🟢 本仓库 PRD / 年报口径 |
| 物种名录（taxa 接口） | **~4000+ 条** 分类记录（含全球种/亚种口径，非「中国已记录种」） | 🟢 `fetch_taxon_list.py` 实测 |
| 中国已记录鸟种量级 | ~1400–1500 种（对应《中国鸟类名录》v3/v4 口径） | 🔵 名录版本推断 |
| 观测记录总量 | **1200 万+ 条**（1980–2024，第三方整理数据集口径） | 🟢 第三方数据集（CnOpenData / CSDN 面板数据） |
| 行政覆盖 | 34 省级 · 344 地级市 · 2672 区县 | 🟢 CnOpenData 数据字典 |
| 单省清单量级（实测锚点） | **云南全省历史 = 69,852 份 checklist** | 🟢 本仓库 `fetch_checklists.py` 实测 |
| 全国 checklist 量级 | **百万级**（云南 ~7 万，且属鸟种最富、最活跃省份之一） | 🔵 由单省实测外推 |

**量级自洽性检查**：若全国清单在 ~100–200 万份，每份平均 ~10 条物种观测 → 千万级观测记录，与第三方「1200 万+」口径吻合。

> ⚠️ 首页那几个官方汇总数字（X 篇报告 / X 次鸟种记录）是 **JS 动态渲染**，静态抓取抓不到；要拿准确实时值，得跑 headless 浏览器或直接向运营方要。

## 2. 对外可观测的数据模型（🟡 高可信）

这是**客户端能直接看到**的实体关系，几乎等同于内部核心表结构。本仓库 `data/process/build_db.py` 已按此建了本地镜像库（三张表）。

```
用户/会员 (member)
      │ 1
      │
      │ N
观鸟报告/清单 (activity / report)   ← 一次外出 = 一条 checklist
      │ 1                               时间 · 省市区 · 点位 · 报告人 · 物种数
      │
      │ N
观测记录 (observation)              ← 报告里的一行：某物种 + 数量 + 出片数
      │ N
      │ 1
物种 (taxon)                        ← 关联分类：目/科/属，名录版本 CH3/CH4
                                      中文名 / 拉丁名 / 英文名

支线：
  地点/热点 (point / location)  —— 经纬度、行政层级、热点系统（清单列表里"不含"经纬度）
  审核层 (audit)               —— 疑问/无疑问标记，异常记录标注（栖息地不符、罕见误报）
```

**关键接口（本仓库实测的现役 schema）**：

| 接口 | 类型 | 作用 | 关键字段 |
|---|---|---|---|
| `POST /front/taxon/search` | 明文 | 全量鸟种名录 | `taxon_id, name, latin_name, english_name, order_name, family_name` |
| `POST /front/record/activity/search` | 加密 | 分页翻 checklist 列表 | `report_id, start_time, province, city, district, point_name, taxon_count, username`（**无 lat/lng**）|
| `POST /front/activity/taxon` | 加密 | 逐报告拿物种观测 | `report_id, taxon_id, taxon_name, taxon_count, record_image_num` |
| 省级概览 | 需签名（响应体明文）| 36 省汇总 | 报告数（疑问/无疑问）、记录总数、鸟种数（含科目分类）|

`report 1—N observation`、`observation N—1 taxon` 的规范化关系，明确指向一个**关系型数据库**。

## 3. 后端技术栈（区分可观测 vs 推断）

### 3.1 可观测（🟡）

- **多端**：Web 站 + 微信小程序（同一套 `/front/*` API）。
- **对象存储**：文件/图片/年报 PDF 放在**阿里云 OSS（杭州区 `bird-bucket.oss-cn-hangzhou`）** → 强烈提示整站托管在**阿里云**。
- **安全/反爬层**（这是最突出的特征）：
  - 前置 **WAF**：校验 `Origin` / `Referer` / `User-Agent`，非浏览器直接拦。
  - **请求体加密**：RSA-1024 PKCS1_v1_5，117 字节分块 + base64（前端公钥 `JSEncrypt`）。
  - **响应体加密**：AES-256-CBC + PKCS7，key/iv 藏在前端 JS。
  - **签名头**：`sign = md5(明文 + requestId + timestamp)`。
  - **captcha 限流闸门**：观测接口 ~40 次/分钟后返回 `code=505`，封会话。
- **数据质量工作流**：报告分「疑问 / 无疑问」，有专家审核 + 异常自动标注 → 后端有一套 review/audit 状态机。

### 3.2 推断（🔵，未确认）

- **DBMS**：极可能是 **MySQL 或 PostgreSQL**（阿里云 + 典型国内 Web 栈 + 规范化关系模型）。千万级行数对单实例 MySQL 完全在射程内，不一定需要分库分表。
- **搜索**：`search` 类接口**可能**后面挂了搜索引擎（如 ES），也可能只是 SQL `WHERE` —— 无法从外部区分。

### 3.3 未公开（⚪）

- 实际 DBMS 产品、服务端框架、真实表结构/索引/分片、总行数、是否有缓存/队列/搜索中间件。
- **这些都得直接问运营方**，外部无从确认。

## 4. 对「合作」的实操建议

1. **别指望爬虫路线**。重度加密 + captcha + WAF 是运营方明确的「不欢迎批量抓取」信号。本仓库的逆向链路只适合做 MVP 演示（如云南前 250 条），**不构成合作基础**，全量早晚撞限流墙。真正合作应走**官方数据共享协议 / 授权 API / 数据库导出**。

2. **对接口**：昆明朱雀会（birdreport.cn 运营方）。合作前先谈清楚**数据授权与使用条款**（民间数据有 licensing 问题）。

3. **该向他们问的清单**（把上面 ⚪/🔵 都问实）：
   - 准确总量：报告数 / 观测记录数 / 已记录物种数（现值）。
   - 后端 DBMS + 表结构，能否提供 **Darwin Core / GBIF 风格**的标准化导出。
   - 授权访问的**速率上限**与鉴权方式（能否给正式 token，绕开 captcha）。
   - **经纬度可得性** —— 清单列表接口不带 lat/lng（本仓库已知痛点），点位/热点数据能否单独拿。
   - 数据许可证 / 署名要求 / 商用边界。

4. **合作能解锁本项目卡点**：拿到官方授权后，PRD 里两个「⚠️ 未解」项（observation captcha 闸门、经纬度缺失）直接消失，P3 分布地图和全量采集才真正可行。
