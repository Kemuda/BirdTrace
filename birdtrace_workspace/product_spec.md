## 1. 产品：BirdTrace 是什么

### 本质：数据已经很好，缺的是从数据到决策的那层界面

从第一性原理推：

1. **观鸟者的问题只有三种形态。** 观鸟数据就三个维度：地点 × 时间 × 鸟种。
   观鸟者的每个真实问题都是固定其中两个、问第三个——
   「我去这里、这个月，能看到什么？」（看什么）
   「我想看这种鸟，什么时候去？」（何时去）
   「这种鸟在哪里、哪个点最值得去？」（去哪看）

2. **回答这些问题的数据已经存在。** 中国观鸟记录中心积累了大量高质量的公民科学
   记录，维度齐全（地点、时间、物种、数量、观察者）。数据不是瓶颈。

3. **瓶颈是界面。** 现在的界面形态是「报告的提交与检索」：用户能查到一份份报告，
   但要自己翻列表、自己数频率、自己判断样本可不可信——数据和决策之间隔着大量
   人肉计算。

4. **这层界面已被验证过。** eBird 用 Explore 证明了它的形态：同一份清单频率数据，
   画成柱图、名录、地图、目标鸟等多种视角，每个视角对应一种问题形态。中文观鸟
   数据还没有对应物。

**BirdTrace 就是给中国的观鸟数据补上这层界面**：把记录组织成三种问题的直接答案——

- **看什么**：选地点和时间 → 鸟种名录，按遇见率排序，样本量透明
- **何时去**：选地点和鸟种 → 全年频率柱图 + 最佳时间窗口
- **探索**：选鸟种或地区 → 分布、热点排行、全年频率规律、近期动态

它不生产数据、不替代记录中心——它让已有的数据回答观鸟者的真实问题，让每一条
公民科学记录产生更多次价值。

**当前 demo 的定位**：这是一个 demo，不是全量产品。真实数据是一个很小的切片——
丽江、拉萨两个城市，2024–2025 两年，且集中在 5–6 月。切片内的每个数字都来自真实
记录（用来证明"这层界面用真数据能跑通"）；切片外的维度用示例数据补齐并显式标注。
所有展示场合都明确说明这一局限。

### 🔒 合作提案方向（内部，提案会前不外发）

我们提议把这层界面作为**中国观鸟记录中心官方出品**的功能，集成进其产品体系。
两种形态，可并行也可分步：

1. **集成进现有网站**：作为记录中心网站的「探索」模块，与现有的记录提交/检索
   互补——用户交完记录，就地看到数据能回答什么。
2. **独立小程序**：官方小程序，面向移动端和出行中的观鸟场景。

**角色分工**：产品官方出品，数据与品牌归记录中心；BirdTrace 开发者以外部开发 /
辅助身份参与共建。数据侧的共建方向（空白格激励 §10.1、鸟点主数据整理 §10.2）
均为提案，与朱雀会共同确认后再启动。

（此节为提案会的谈话方向，属内部策略；正式出对外文档时删除，会上口头呈现。）

**产品原则（贯穿所有功能）：**

- **数据诚实**：每个数字标来源、覆盖范围、样本量；样本薄的地方明确说薄；真实数据
  与示例数据绝不混淆（§5 为硬约束细则）。
- **答案优先**：页面第一眼是结论（速读条、最佳窗口、最优鸟点），推导过程和口径
  说明收在一层之下，需要才展开。
- **开放的数据接口**：数据层与展示层解耦（§6.2），可平滑接入更多数据源。

*本文档其余部分定义当前迭代的功能范围（§3–§4）、约束（§5–§7）与验收标准（§8）。*

## 2. 核心用户故事

以下用户故事覆盖本轮所有七个功能模块。

**US-01（看什么）**
作为一名已经定了目的地和时间的观鸟者（比如下个月去丽江），我希望在「看什么」页面：
先看到这个城市能看什么鸟、有哪些鸟点；再收敛到某个具体鸟点，看它的名录和各种鸟的
遇见率——在时间、方向都确定的前提下，完成从城市到鸟点的探索。

**US-02（鸟种分布图）**
作为一名想了解某种鸟在全国分布规律的观鸟者，我希望选择一个鸟种后能看到一张地图，地图上的圆点大小反映记录数量、颜色区分季节，以便快速判断该鸟在哪些区域、哪个季节记录最集中。

**US-03（地区探索页）**
作为一名规划去某个具体地区的观鸟者，我希望进入一个地区概览页面后能看到该地区的热点地图、按频率排序的鸟种列表、全年季节直方图和近期记录流，以便在出发前对这个地区的观鸟资源有整体认知。

**US-04（多物种柱图）**
作为一名需要协调多个目标鸟种出行时间的观鸟者，我希望在柱图页面能同时叠加多个鸟种的频率曲线，以便直观看到多个目标鸟种的时间窗口交集，做出最优行程安排。

**US-05（频率网格）**
作为一名想快速扫视某地区整体鸟种年度规律的观鸟者，我希望通过一张行=鸟种、列=月份、格子深浅=当月出现频率的网格，快速找到哪些鸟种在哪个月最值得关注，而不必逐个鸟种点击查看。

**US-06（目标鸟种）**
作为一名有个人观鸟记录的用户，我希望在「看什么」页面能切换到「该地区有、但我还没见过」的视角，按频率排序浏览缺失鸟种，以便高效规划本次出行的新增目标。

**US-07（近期记录流）**
作为一名计划近期前往某地区的观鸟者，我希望在地区探索页能看到按时间倒序排列的最近观测报告，了解哪些人在什么时间记录了哪些鸟，以便判断近期该地区的活跃程度和数据新鲜度。

### 🔒 内部用户故事（交付版删除）

**US-08（数据诚实性，对演示受众）**
作为中国观鸟记录中心的数据负责人，我希望真实数据功能清晰标注来源和覆盖范围，示例数据功能有独立的「示例数据」标注，以便明确区分 BirdTrace 当前真实数据覆盖范围和演示阶段的功能，避免对数据质量产生误判。

**US-09（数据源可切换，对工程团队）**
作为 BirdTrace 工程团队成员，我希望所有功能的数据层与展示层解耦，数据源可在示例数据、中国观鸟记录中心导出文件和 eBird API 之间切换，以便演示后不改前端逻辑即可接入新的数据源。

## 3. MVP 范围

### 数据现状（决定每个功能的定位，先读这个）

当前真实数据是一个很小的切片，三个局限：

1. **空间**：只有云南 + 西藏部分地区，demo 只开放丽江、拉萨两城。
2. **时间**：2024–2025 两年，且**集中在 5–6 月**（行程驱动抓取的产物；云南有少量
   1/2/3/12 月省级样本，西藏基本只有 6 月 + 一次"最近"扫）。
3. **推论**：任何按 12 个月展开的可视化（频率网格、多物种柱图、季节直方图），
   5–6 月之外的格子/柱基本是空的或极薄——**用纯真实数据画不出"全年规律"**。

因此 **MVP 整体定位是 demo**：交互层全部做真，数据层"真实切片 + 示例数据"并用——
真实切片（丽江/拉萨、5–6 月）证明界面用真数据能跑通；全年维度、全国尺度用示例
数据补齐并显式标注（§5 硬约束）。后续两条路都开着：按维度补拉数据，或继续用
标注过的示例数据，等数据合作后整体替换。

### 本次做什么

| 功能模块 | 数据状态 | 定位 |
|---|---|---|
| 「看什么」polish | 真实切片（丽江/拉萨） | demo · 真实数据主打 |
| 鸟种分布图 | 示例数据（全国尺度，超出覆盖） | demo · 示例数据 |
| 地区探索页 | 真实切片（regions/*.json 已有；季节直方图会显出 5–6 月偏斜，如实展示） | demo · 真实数据主打 |
| 多物种柱图 | 真实数据画 5–6 月真实、其余月份稀疏；演示预设选有跨月数据的云南鸟种，或切换示例数据版并标注 | demo · 真实+示例并用 |
| 频率网格 | 同上——真实版如实显示稀疏（本身就是诚实性展品），可另备示例数据版演示"数据全了是什么样" | demo · 真实+示例并用 |
| 目标鸟种 | 真实切片 + 本地个人标记（useMarks） | demo · 真实数据主打 |
| 近期记录流 | 真实切片（时间范围如实标注） | demo · 真实数据主打 |

**并用规则**（§5 硬约束的推论）：同一图表内不真假混排；示例数据版整体切换、整体
标注（provider isDemo），与真实版一键切换正是给数据方看的接口能力。

### 本次不做什么

以下内容明确排除在本轮范围之外，不因工期宽裕而提前纳入：

- **账号系统的实现**（注意：账号系统已确认为**产品必备**，见 §9——目标鸟种依赖
  用户的历史标记数据，没有账号承载不成立。只是不在本轮交付：本轮 demo 用本地
  useMarks + 导出/导入备份过渡）。
- **完整移动端 IA**（底部 tab 导航、独立 MobilePage 组件，见 design_spec §2）：基础
  响应式断点（≤640px）已在 public demo 轮上线，新功能只需不破坏该断点即可；完整
  移动端信息架构留后续。
- **点位详情页（Hotspot 档案页）**：基础元素与地区探索页相同（地图定位、频率名录、
  季节直方图、近期记录——组件可全复用），建页本身成本低；真正的前置是鸟点主数据
  整理（§10.2）。本轮不建。
- **AI 自然语言摘要**（"夏候鸟已到齐…"）：本轮 Backlog，不做。
- **居留型标签**（留鸟/夏候/冬候/旅鸟）：推断准确度未满足，权威数据源未接入，本轮不展示。
- **「何时去」页的旬级下钻**：月级足够演示，旬级待后续。
- **分布图接入真实坐标数据**：本轮只用 filler 示例数据，坐标数据管线（GCJ-02 验证、高德 key 申请）不在本轮交付。
- **eBird API 的实际集成与数据拉取**：仅规划切换接口，本轮不做实际 API 调用。
- **实时数据同步 / 在线后端服务**：静态 JSON 导出方式不变，本轮不引入任何在线后端。
- **敏感物种坐标脱敏处理**：依赖与数据方的治理协议，演示前不触碰。
- **频率网格的市/县级下钻**：本轮仅做省级，数据粒度匹配 province bundle。
- **近期记录流的明细完整抓取**：「明细待抓」状态诚实标注，不在本轮补抓。
- **目标鸟种的跨地区合并视图**：仅支持单次选定的地区范围。
- **export_json.py 的后续改动**（除近期记录流可选新增 recent.json 聚合导出外）。
  注：spot 级 `district` 字段已在 public demo 轮加入 region_bundle，但 Amber 决定暂不
  重跑导出启用；该字段不算本轮改动额度。
- **地区间横向对比、用户自定义区域划定、历史趋势（多年对比）**。
- **社区目标鸟**（eBird Community Targets）：「今年还没人报」的语义需要当年实时
  数据，我们是 2024–25 静态快照，不成立。数据管线支持增量更新后再评估。
- **周级（48 格）频率柱图**：导出是月粒度。记 Backlog（迁徙种过境窗口月级分辨不出）。
- **置信度徽章**（对应 birdreport「疑问/无疑问」审核字段）：值得做，但当前抓取
  管线没存该字段。记 Backlog，等数据合作后从源头拿。

## 4. 各功能模块详述

### 4.0「看什么」Polish（生产可用，真实数据）

**目标：** 让已有功能在演示中展现最佳状态，不引入新功能，不改动数据层。

**基线（v2.1 更新）：** 「看什么」的地点选择器已是两维结构（城市 + 鸟点），对外版
城市锁定丽江市 + 拉萨市，鸟点为规范化合并后的列表（下拉只显示"名称（区县）"，
数字与合并说明在下方 chip）。对外版直接进入"该点全部记录"名录，不带 6 月行程框架。
Polish 在此基线上进行。

**Polish 范围（仅限以下条目，不扩大）：**

- 数据诚实性文案：检查「thin 数据」黄条提示、N<15 斜纹标注的措辞是否准确，对演示受众（数据专家）来说是否足够清晰。
- 空态提示：当某地某月真无数据时，提示文案需说明原因（无记录 vs 数据未导入），避免受众误解为系统 bug。
- 报告列表弹窗：确认报告链接可点通、「明细待抓」标注清晰（对外版该注释按 IS_PUBLIC 约定隐藏）。
- 导出鸟单：确认导出功能可用，导出文件头部标注数据来源和日期范围。
- 鸟点规范化别名表（`lib/spots.js` ALIASES）：演示前把丽江、拉萨两市的鸟点下拉逐项过一遍，
  发现没归拢的写法/漏网垃圾条目就补表。这是数据展示质量的最后一道人工核对。
- 页面性能：确认在演示机上首屏加载时间可接受（无需量化指标，视觉感知流畅即可）。

**不做：** 改变数据逻辑、频率计算方式；地点选择器不再动结构（两维结构即最终形态）。

### 4a. 鸟种分布图（demo 展示，filler 示例数据）

**用户问题：** "这种鸟在哪里、哪个季节最常见？"

**定位说明：** 鸟种分布图需要全国尺度的坐标数据，超出当前数据覆盖范围，是七个功能中唯一保持 filler/demo 定位的功能。

**交互逻辑：**
- 入口：「探索」tab 落地页的分布图入口，或从「看什么」名录中的鸟种行进入。
- 输入：单个鸟种（中文名，支持模糊搜索）。
- 输出：地图上显示若干圆点，每个圆点代表一个记录地点。
  - 圆点大小：正比于该地点的历史记录数量。
  - 圆点颜色：区分季节（春/夏/秋/冬四色，以记录最多的季节为准）。
- 地图可缩放/平移。点击圆点显示：地点名称、记录数量、记录季节分布。

**数据要求：**
- 本轮全部使用 filler 示例数据。鸟种名称、地点名称使用真实名称，记录数字和坐标为合理构造的示意值。
- 示例数据在界面上以固定标注「示例数据」呈现（见第 5 章硬约束）。
- filler 数据结构需与未来真实数据格式一致（字段名、数据类型相同），以便后续切换数据源无需改前端。

**不做：** 跨多鸟种叠加分布图、时间轴动画、迁徙路径连线。

---

### 4b. 地区探索页（生产可用，真实数据）

**用户问题：** "去这个地区观鸟，整体情况怎么样？"

**定位说明：** 现有 regions/*.json 导出已包含热点坐标、鸟点排行、月份直方图、概览统计，地区探索页使用真实数据。当前数据覆盖云南 + 西藏，页面上明确展示覆盖范围说明，不覆盖的地区显示「暂无数据」。

**交互逻辑：**
- 入口：「探索」tab 落地页选择地区，或从「看什么」的地点选择器直接跳入。
- 输入：地区（省 / 市 / 区县，使用现有地点选择器层级）。
- 页面包含以下四个区域（布局顺序不约束，工程自定）：

  **区域一：地区概览**
  记录鸟种总数、报告总份数、数据覆盖年份范围。数字来自 regions/*.json 真实导出。

  **区域二：热点地图**
  该地区内观鸟热点的地图分布，圆点大小正比于热点报告数量。点击热点显示热点名称和报告数。坐标来自 regions/*.json 真实导出。

  **区域三：鸟种列表（按频率排序）**
  该地区报告频率最高的若干鸟种（建议 20~50 种），显示：中文名、频率百分比、最佳月份。数据来自真实导出。

  **区域四：季节直方图**
  该地区全年 12 个月的报告数量柱状图（报告数量，不是鸟种频率），帮助用户判断哪个月份记录最活跃。数据来自真实导出。

  **区域五：近期记录流**（见 4f，作为地区探索页的内嵌区块）

**数据范围说明文字：** 页面需明确展示「当前数据覆盖：云南、西藏」，不覆盖其他省份。

**不做：** 地区间横向对比、用户自定义区域划定、历史趋势（多年对比）。

### 4c. 多物种柱图（生产可用，真实数据）

**用户问题：** "我有几个目标鸟种，什么时间去能同时覆盖最多？"

**现状：** 「何时去」页面已有单物种 12 月柱状图，底层 bundle 数据已支持多物种查询。本轮扩展交互层，在原地升级，不独立建页。

**交互逻辑：**
- 在现有「何时去」页面增加「添加对比鸟种」入口。
- 支持同时叠加 2~4 个鸟种的频率曲线（超出 4 种不做，演示足够）。
- 每条曲线/柱使用不同颜色，颜色与图例一一对应。
- 多物种叠加时，在图表下方或图表内突出标注「窗口交集」（所有选中鸟种频率均达到一定阈值的月份区间），阈值定义由工程自定（建议：各鸟种当月频率均 > 10% 或均 > 各自峰值的 50%，取其一，演示合理即可）。

**鸟种选择器：**
- 在现有搜索框旁增加「+ 添加鸟种」按钮，点击后可搜索并添加，支持删除已添加鸟种。
- 鸟种选择器使用现有 taxa 数据（真实数据），不需要 filler。

**数据状态说明：**
- 叠加图本身的频率数据：如果当前 bundle 有该鸟种数据，使用真实数据；如果没有，显示「暂无数据」占位（不用 filler 填充）。

**不做：** 旬级下钻叠加、导出叠加图、曲线交互式悬停数据点弹窗（基础版即可）。

### 4d. 频率网格（生产可用，真实数据）

**用户问题：** "在这个地区，哪些鸟种在哪个月最值得关注？"

**对标：** eBird Illustrated Checklist / Bar Charts。

**形态：** 网格视图，行 = 鸟种，列 = 12 个月，格子深浅 = 当月出现频率。

**数据来源：** province bundle 已有每种 × 12 月的计数与分母，可直接计算频率，无需新增数据管线。

**交互逻辑：**
- 入口：「探索」tab 落地页的频率网格入口。
- 输入：省份选择（与现有地点选择器联动，限当前数据覆盖的省份）。
- 输出：
  - 行为鸟种，列为 1–12 月。
  - 每格颜色深浅正比于该鸟种当月出现频率；频率为 0 的格子有明显视觉区分（如空白或灰底）。
  - 鸟种行可按最高频率月份或按科属排序，排序方式可切换。
  - 点击单个格子，显示该鸟种该月的频率数值（百分比）和样本量 N。
- 页面明确展示数据覆盖省份范围。

**数据诚实性：**
- N 过小（建议阈值由工程自定，参考 N<15）的格子以视觉方式标注（如斜纹或半透明），不以粗暴清零处理。
- 数据来源标注（中国观鸟记录中心）在第一屏内可见。
- **分母行（v2.2）**：网格底部一行显示各月完整报告数（分母）。eBird 把分母藏在
  CSV 下载里，我们直接摆明面——演示受众是数据方，这是诚实性卖点。

**不做：** 市/县级下钻、跨省对比、导出网格图、格子动画、周级（48 格）分辨率
（月粒度导出撑不住，记 Backlog——迁徙种过境窗口月级分辨不出，是真实需求）。

### 4e. 目标鸟种（生产可用，真实数据 + 本地标记）

**用户问题：** "该地区有哪些我还没见过、又值得去找的鸟？"

**对标：** eBird Target Species。

**信息架构位置：** 作为「看什么」页面的一个筛选视角，不是独立页。用户在「看什么」页面可切换「全部鸟种」/ 「目标鸟种」视角。

**逻辑：**
- 基础名录：地区鸟种名录（来自 regions/*.json 或 province bundle，真实数据）。
- 个人标记：useMarks 本地数据中用户标记为「已见」的鸟种。
- 目标鸟种 = 地区名录 − 已见鸟种，按该地区频率从高到低排序。

**交互逻辑：**
- 「看什么」页面出现「目标鸟种」切换入口（按钮或 tab）。
- 切换后，名录仅显示未见鸟种，频率排序与原名录一致。
- 已见状态的标记/取消标记操作不变，操作后列表实时更新。
- 若 useMarks 为空（用户无任何标记），目标鸟种视角与全部鸟种视角相同，并提示「标记已见鸟种后，此处将只显示未见鸟种」。

**数据诚实性：**
- 本功能数据来自真实名录与本地标记，无需「示例数据」标注。
- 名录数据来源标注与「看什么」页面保持一致。

**账号依赖说明：** 用户标记是本功能的核心输入，只存 localStorage 换设备即丢——
账号系统因此是产品必备（§9）。本轮以本地 useMarks + 导出/导入备份过渡，账号上线
后本地数据一键迁移并入。

**不做（本轮）：** 云端同步（随 §9 账号系统交付）、跨地区合并目标鸟种视图、稀有度或难度标注。

### 4f. 近期记录流（生产可用，真实数据）

**用户问题：** "这个地区最近有什么新的观测记录？"

**对标：** eBird Recent Visits。

**信息架构位置：** 作为地区探索页（4b）的一个内嵌区块，不是独立页。

**形态：** 按时间倒序展示最近的观测报告列表。每条记录显示：日期、观测地点、鸟种数、「明细待抓」诚实标注（复用现有机制）。有明细的报告可展开或跳转查看鸟种列表。

**数据来源：**
- 优先从现有导出文件中提取最近 N 条报告（N 由工程自定，建议 20~50 条）。
- 如现有 regions/*.json 中已包含足够的近期报告数据，直接使用，不新增导出文件。
- 如现有导出文件不满足需求，可选新增 recent.json 聚合导出（这是本轮允许的唯一数据管线改动，且为可选项）。

**数据诚实性：**
- 「明细待抓」状态诚实标注，不在本轮补抓，不用虚假明细填充。
- 数据来源和时间范围在区块头部标注。

**不做：** 跨地区合并近期记录、用户评论或社交功能、推送通知、明细的完整补抓。

### 4g.「招牌种」badge（加分项，可选，真实数据）— v2.2 新增

**用户问题：** "这个鸟点相对别处强在哪，值不值得专程去？"

**对标：** eBird Iconic Birds（研究 §5.5——"本轮研究最值得抄的一个概念"）。
纯频率榜答不了"值不值得专程"：麻雀在哪都 90%。需要**相对量**：本点频率 ÷ 区域基线。

**逻辑（简化版）：**
- `招牌指数 = 该种在本点的频率 ÷ 该种在全省的年频率`
- 省频率由 province bundle 的 species 12 月计数 ÷ total_reports 求得；点频率来自
  points/*.json。两个既有文件，客户端算，不动导出管线。
- 门槛：倍数 > 3 且该点样本 N ≥ 5 才显示；每点最多标 3 种，防滥。

**呈现：** 鸟点叶子页名录中，命中的种加金色小 badge「全省 N 倍」+ ⓘ 口径说明。

**定位：加分项。** 做不完不阻塞演示；做完了是演示的高光时刻（"你们的数据能直接
回答'值不值得专程'——这是纯排行榜给不了的"）。

**不做：** eBird 原版的 10 年窗口/30% 年份门槛（我们数据只有 2024–25，简化门槛即可）、
跨点横向对比页。

## 5. 数据诚实性要求（硬约束）

本章为独立硬约束，优先级高于所有其他功能细节，不可因工期压力被降级。本章规则覆盖全部七个功能模块。

### 5.1 为什么这是硬约束

演示对象是中国观鸟记录中心和昆明朱雀会，他们是数据的产生者和维护者。「用你们的数据做出来的」比漂亮的假数据更有说服力；若演示中的数字让他们误以为来自他们的真实数据库而实为虚构，将直接破坏建立合作关系的基础。真实数据功能必须清晰标注来源和覆盖范围，示例数据功能必须有独立的「示例数据」标注。

### 5.2 标注规则

**规则 1：示例数据必须显式标注。**
所有使用 filler 示例数据的页面或区域，必须在用户可见的位置显示「示例数据」标注。标注不得使用仅工程团队可见的注释或 URL 参数，必须是界面元素。

**规则 2：标注位置和形式。**
标注应出现在：页面标题区或数据区域的头部，在第一屏内（无需滚动可见）。具体视觉形式由工程自定，但必须在视觉上与正文数字有明显区分（如 badge、色带、注释行），不得以小字脚注埋在页面底部。

**规则 3：真实数据不得与示例数据混排在同一图表/列表中，不加区分。**
如果某功能的部分数据是真实的、部分是示例的，必须分区展示并分别标注，或者整体使用一类数据。不允许出现「图表里有真有假、用户无法区分」的状态。

**规则 4：示例数据的内容应真实合理但数字为构造值。**
鸟种名称、地点名称使用真实名称（避免在演示中出现明显虚构内容引发困惑），但记录数量、频率数字为合理构造的示意值（不声称来自真实观测统计）。

**规则 5：数据源可切换，切换不改前端展示逻辑。**
filler 示例数据与真实数据使用同一字段结构。切换数据源由 provider 层的 isDemo 标记驱动：isDemo=true 时展示「示例数据」标注，isDemo=false 时标注自动消失，无需人工记得摘除，不依赖前端代码修改。

### 5.3 真实数据功能的标注要求

使用真实数据的功能（看什么、地区探索页、多物种柱图、频率网格、目标鸟种、近期记录流）必须保留并清晰展示：
- 数据来源：中国观鸟记录中心（birdreport.cn）。
- 数据覆盖范围（当前为云南 + 西藏）。
- 数据覆盖年份范围（`report_years` 字段，当前为 2024+2025）。
- 样本量 N，N<15 的月份/格子灰化并标注「仅供参考」或同等提示。
- 「明细待抓」状态诚实标注（不可在演示前悄悄移除）。

## 6. 非功能需求与架构约束

### 6.1 静态优先

维持「静态 JSON 导出 + 纯前端 SPA」形态，本轮不引入任何在线后端服务。所有数据均来自本地或预先导出的静态文件。

### 6.2 数据 provider 层

- 页面组件只依赖统一数据接口，不直接绑定具体数据文件或 API 端点。
- 数据源可在 filler 示例数据、birdreport 导出文件、未来 eBird API 之间切换。
- 「示例数据」标注由 provider 层的 isDemo 标记驱动。切换为真实数据后，标注自动消失，不依赖人工记得摘除，不改前端展示代码。

### 6.3 信息架构

- 顶部导航（对外版）：看什么 / 何时去 / 探索（新增），共 3 个 tab。
  dev 版另有「去哪看」占位 tab（`devOnly` 标记，IS_PUBLIC 时过滤），不算在 3 个之内。
- 「探索」tab 为落地页，内含三个功能入口：分布图、地区探索、频率网格。
- 目标鸟种：作为「看什么」页面的一个筛选视角（切换入口），不是独立页。
- 近期记录流：作为地区探索页的一个内嵌区块，不是独立页。
- 多物种柱图：在「何时去」页面原地升级，不是独立页。
- 对外/dev 差异统一走 `lib/mode.js` 的 `IS_PUBLIC` 常量（构建时注入），不引入运行时开关。
- **URL 深链（v2.2）**：探索子页走 `&sub=distribution|region|grid`；「看什么」当前
  城市/鸟点写进 `&r=`。目标：演示者能把任意具体视图存书签/直链。后续参数族
  （`&m=` 月份、`&spp=` 鸟种）见 design_spec §3.4，本轮不做。

### 6.4 数据管线改动最小化

- 七个功能中，仅「近期记录流」在现有导出文件不满足需求时，可选新增一个 recent.json 聚合导出文件。
- 其余六个功能不改动 export_json.py，不新增数据导出脚本。
- 此条为工程硬约束，演示前不因功能需要而突破。

## 7. 边界与异常情况

### 7.1 真实数据边界（地区探索页、频率网格、近期记录流）

- 当前数据覆盖云南 + 西藏。选择覆盖范围外的省份/地区，页面显示「当前暂未覆盖该地区，数据覆盖范围：云南、西藏」，不崩溃，不显示空数据或 0 值。
- 导出文件为静态，演示期间不做动态更新。若演示受众要求查看其他地区，如实说明覆盖范围，不临场构造假数据。

### 7.2 filler 示例数据边界（鸟种分布图）

- filler 数据为静态文件，演示期间不做动态更新。
- 若演示受众要求「换一个鸟种看看」，应提前准备 3~5 个鸟种的 filler 数据，不要临场生成。
- filler 数据中不得出现国家级保护动物的精确坐标（即使是虚构坐标，也需避免在演示中引发敏感物种坐标的讨论）。

### 7.3 多物种柱图异常情况

- 用户添加的鸟种在当前 bundle 无数据：显示「该地区暂无此鸟种数据」，不崩溃，不用 filler 填充。
- 用户添加超过 4 个鸟种：显示提示「最多同时对比 4 个鸟种」，不允许继续添加，不崩溃。
- 窗口交集为空（所有月份均有至少一个鸟种低于阈值）：显示「所选鸟种无共同最佳时间窗口」，而非空白或报错。

### 7.4 地图相关异常

- 地图加载失败（网络问题、key 过期等）：显示文字占位，说明地图暂时无法加载，页面其余内容正常展示。
- filler 示例数据中的坐标落点偏移或不精确：演示前人工核查一遍落点是否在正确区域内，避免明显错误被受众发现。

### 7.5「看什么」polish 边界

- 已有功能的任何数据层改动都不在本轮范围。如果 polish 过程中发现数据层 bug，记录到 TODO 但不在本轮修复。

### 7.6 目标鸟种异常情况

- useMarks 为空（用户无任何标记）：目标鸟种视角与全部鸟种视角相同，并在列表上方显示引导提示「标记已见鸟种后，此处将只显示未见鸟种」。
- 地区名录为空（该地区暂无鸟种数据）：显示「该地区暂无鸟种数据」，与全部鸟种视角的空态处理一致。

### 7.7 频率网格异常情况

- 某鸟种某月 N=0（无记录）：格子显示为空白或特定底色，不显示 0%，与有频率数据的格子有明显视觉区分。
- 省份选择超出数据覆盖范围：显示「当前暂未覆盖该省份」，不显示空网格。

### 7.8 近期记录流异常情况

- 导出文件中无近期报告数据：区块显示「暂无近期记录」，地区探索页其余区块正常展示。
- 报告明细为「明细待抓」状态：标注清晰，不展开，不显示虚假明细，不崩溃。

### 7.9 数据源切换边界

- 切换配置方式（环境变量、config 文件等）由工程自定，但切换必须不改前端展示代码。
- 本轮只需保证「示例数据 → 真实数据」的切换路径设计清晰，不需要真正跑通切换。

## 8. 验收标准

以下条目可被 tester agent 逐条核对。每条标注对应功能模块。

### 8.1「看什么」Polish

- **AC-01**：打开「看什么」页面（对外版），城市选「丽江市」，鸟点下拉出现规范化合并后的
  鸟点列表（无"位置"等垃圾条目、无纯行政区名、无重复同名点）；选任一鸟点，页面正常加载
  显示该点鸟种名录，无报错、无白屏。
- **AC-01b**：鸟点下拉的 option 文本只含"名称（区县）"（区县数据未导出时只有名称）；
  鸟种数/清单数/"合并 N 处"等信息出现在选择器下方的 chip 中，不混在 option 文本里。
- **AC-01c**：选中一个由多处同名点合并成的鸟点（如拉市海），名录数据为全部合并 point_id
  的记录之和（清单数 = 各原始点之和），且页面有"合并 N 处"的透明标注。
- **AC-02**：名录中存在 N<15 的月份时，对应柱图显示斜纹样式，且旁边有「仅供参考」或等效文字提示。
- **AC-03**：页面头部或数据区域可见「数据来源：中国观鸟记录中心」字样，并展示数据年份范围（如「2024–2025」）。
- **AC-04**：点击某鸟种行的「N 份报告」按钮，弹窗正常展开，显示报告列表；列表中「明细待抓」状态的报告有对应文字标注，且不显示虚假的物种明细。
- **AC-05**：点击「导出鸟单」，下载的文件头部包含地区名称、时间段、数据来源信息，不是裸列表。
- **AC-06**：选择一个真实无观测数据的地区 + 月份组合，页面显示「无记录」或等效空态提示，不崩溃，不显示 0% 频率的虚假列表。

### 8.2 鸟种分布图（filler/demo）

- **AC-07**：从「探索」tab 进入分布图，搜索「黑颈鹤」，页面加载地图，地图上出现至少 3 个圆点，圆点大小不完全相同。
- **AC-08**：页面第一屏内（无需滚动）可见「示例数据」标注，标注为界面元素（非 URL 参数、非隐藏注释）。
- **AC-09**：圆点颜色至少有 2 种以上颜色，图例中有颜色与季节的对应说明。
- **AC-10**：点击任意圆点，弹出信息包含：地点名称、记录数（示意值）、季节信息，不崩溃。
- **AC-11**：地图支持缩放（通过滚轮或触控板），缩放后圆点位置保持正确，不飞点。
- **AC-12**：搜索一个 filler 数据中不存在的鸟种（如搜索乱码字符串），页面显示「未找到该鸟种数据」，不崩溃，不显示空地图而无任何提示。

## 9. 账号系统与用户协议（产品必备，排期另定）

### 9.1 账号系统

**为什么必须有：** 目标鸟种 = 地区名录 − 用户已见。用户的标记（已见/目标/笔记）
是这个功能的输入，只存浏览器 localStorage 换设备即丢。账号是产品必备，不是可选项。

**最小形态：** 轻量登录（方式由工程选型）+ 标记云端同步 + 现有本地 useMarks
一键迁移导入。

**排期：** 不在本轮 demo 交付内。本轮以本地标记 + 导出/导入备份过渡；账号上线后
本地数据自动并入，用户无感迁移。

### 9.2 用户协议（要点）

1. **非商用、不收费。** BirdTrace 不做商业用途，不向用户收费。
2. **数据归用户。** 观测记录的所有权归用户个人。平台使用的是聚合（aggregate）后的
   数据；平台不主张对用户数据的所有权。
3. **CC 4.0 共享。** 聚合数据以 CC 4.0 协议对外共享，供所有人使用。
   （待定稿：明确具体变体——鉴于第 1 条非商用立场，CC BY-NC 4.0 与之更一致；
   若希望学术/生态研究无障碍引用，CC BY 4.0 更开放。发布前需确认。）
4. **默认入池、可退出。** 用户数据默认进入共享数据池；用户可随时 opt out，退出后
   其数据不再进入后续发布的聚合数据。

条款细化与法务审校在协议正式发布前完成。界面呈现（注册时告知、设置页 opt-out
开关）随账号系统一起交付。

## 10. 未来方向（for future reference，不排期）

**10.1 数据空白格激励（25km 网格）**

中国观鸟记录中心的数据有一个 25km × 25km 方格维度。西部大量方格是空白——从没有
人在里面提交过记录。记录中心希望鼓励观鸟者去这些空白区域采集数据。

潜在功能：把「空白格」做成一个探索图层——地图上显示哪些方格还没有任何记录，
引导用户去补。这与 eBird 的「社区目标鸟」同属把集体数据缺口游戏化的思路，但
针对的是空间缺口而非物种缺口。

- 产品位置未定：可能挂在分布图图层、地区探索页，或独立的「任务/挑战」入口。
- 价值：与数据方自己的增长诉求直接对齐，是数据合作谈判里的天然共建话题。
- 依赖：需要记录中心提供方格级覆盖数据（或从坐标聚合自算）。

**10.2 鸟点主数据与 Hotspot 档案页（志愿者整理 · 提案，需与朱雀会同步确认后启动）**

**问题：** 记录中心的点位大量是用户自建的——「随手记 / 定点记」的产品设计使然，
产出很随意（arbitrary）：名字不统一、同地多点（丽江老君山一个地方就有多个重复点）。
前端现有的规范化合并层（`lib/spots.js` 别名表）是权宜之计，靠人工补表，不成体系。

**计划：** 组织志愿者按城市整理**权威鸟点表**：每个点的正式名、别名列表、坐标、
归属区县。优先级按记录量排——先整理每个城市的热门鸟点，覆盖到该城约 95% 的记录
即可；长尾点继续走自动规范化兜底。整理成果替换前端别名表，升级为数据层的一部分
（点位 id 映射表）。

**随之解锁：** Hotspot 档案页——基础元素与地区探索页完全相同，组件全复用，主数据
就绪后低成本上线。对标 eBird 的热点体系（含志愿者维护的 About 页，研究 §6.3）。

**价值：** 这项整理对数据方自身就是点位数据治理，是继空白格激励之后的又一个
合作共建点。

**10.3 其它已记录的 Backlog**

周级（48 格）频率柱图 · 置信度徽章（对接审核字段）· 完整移动端 IA（design_spec §2）。
